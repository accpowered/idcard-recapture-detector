## 1. 批量处理：选多图后提示「轮询失败：HTTP 200」

### 现象
- 批量页选择多张图片 → 点击「开始处理」→ 页面显示 `轮询失败：HTTP 200`。
- 实际上 `POST /api/batch` 与 `GET /api/batch/{id}` 都是 HTTP 200，识别本身在后台正常完成。

### 证据
- `POST /api/batch` 返回 `{"code":0,"task_id":"..."}`。
- `GET /api/batch/{task_id}` 返回任务对象，keys 为：
  `created_at, done, errors, finished_at, id, model_version, results, status, total`，**没有 `code` 字段**。

### 根因
- 前端统一请求封装 `api()`（v1.1 新引入）用 `body.code !== 0` 判断失败；
  对于没有 `code` 的响应，`undefined !== 0` 为真 → 直接抛错；错误信息回退为 `HTTP + 状态码`，即 `HTTP 200`。
- `/api/batch/{task_id}` 是 v1.0 遗留接口，未纳入 v1.1 的 `{code:0,...}` 响应约定；前端封装以偏概全。

### 修复
- 后端新增 `ApiOps.batch_status(task_id)`：成功返回 `{"code":0, ...任务对象}`；任务不存在返回 404 + `{"code":404,"error":...}`。
- `app/main.py` 与 `app/run_stdlib.py` 的批量轮询路由改为调用 `ops.batch_status()`。
- 前端 `api()` 改为仅当 `code` 存在且不为 0 时抛错；`pollBatch` 处理 `status=not_found`，完成时展示失败张数。
- 回归测试：标准库服务测试新增 `GET /api/history` 与 `GET /api/batch/not-a-real-task` 断言。

### 涉及文件
- `app/web/app.js:47`（code 判空兼容）、`app/web/app.js:263-295`（轮询与 not_found）。
- `app/api/ops.py:106-110`（batch_status）、`app/main.py:55-57`、`app/run_stdlib.py`（批量轮询路由）。

## 2. 历史加载：服务返回异常（HTTP 500）

### 现象
- 历史页提示 `历史加载失败：服务返回异常（HTTP 500）`。
- 服务端 traceback（来自 8011 复现）：

      File "app/main.py", line 153, in history
        return {"code": 0, "items": ctx.storage.list_history(limit, offset)}
      File "app/services/storage.py", line 59, in list_history
        rows = c.execute("SELECT * FROM history ORDER BY created_at DESC LIMIT ? OFFSET ?", ...)
      sqlite3.OperationalError: unable to open database file

### 根因链
1. 该查询是 `SELECT * ... ORDER BY ... LIMIT/OFFSET`，SQLite 在执行外排排序时需要创建**临时文件**；
   只查 `id`（小行）时可完全在内存中完成，所以不一定报错。
2. SQLite 原生在 Windows 通过 `GetTempPath()`（即 `%TEMP%`）创建临时文件；当前启动环境下 `%TEMP%` 对进程不可写。
3. Python 的 `tempfile` 会回退到工作区目录，掩盖了 TEMP 不可写；SQLite 不会回退，于是报 error 14 `unable to open database file`。
4. 因此与数据库内容/损坏无关：同样的库在“普通终端”里可读，在受限终端启动的服务里稳定 500。

### 证据矩阵（同一进程、同一数据库）

| 查询/操作 | 默认 `temp_store=0` | `PRAGMA temp_store=MEMORY` |
| --- | --- | --- |
| `SELECT id ... ORDER BY created_at DESC LIMIT 5` | 成功（内存） | 成功 |
| `SELECT * ... ORDER BY created_at DESC LIMIT 5` | **失败：unable to open database file** | 成功 |
| `SELECT * ... ORDER BY ... LIMIT 5 OFFSET 0` | **失败** | 成功 |
| `SELECT * ... ORDER BY ...`（无 LIMIT） | **失败** | 成功 |
| 直接向 `%TEMP%` 写文件 | `PermissionError(13)` | — |

### 修复
- `app/services/storage.py` 的 `_conn()` 统一设置 `PRAGMA temp_store=MEMORY` 与 `PRAGMA busy_timeout=5000`。
  历史/反馈数据量很小（只影响排序键与读取，不做大数据计算），内存排序无压力，且彻底摆脱 TEMP 依赖。
- 新增 `tests/test_storage.py`：写入含 200KB `annotated_b64` 的历史后必须能 `list_history` 成功；反馈读写同样覆盖。
- `tests/test_stdlib_api.py` 增加真实 `GET /api/history` 调用，防止路由层再次 500。

### 为什么之前测试没发现
- 原测试只覆盖 fields/signals/pipeline，没有任何 Storage 或 `/api/history` 用例。
- 之前的临时目录状态可能可写，问题不显现；本次服务启动环境触发了它。

### 涉及文件
- `app/services/storage.py:20-34`（PRAGMA）、`:65-67`（list_history）。
- `tests/test_storage.py`（新增）、`tests/test_stdlib_api.py`、`tests/run_tests.py`。

## 3. 首页：无 OCR 时不要显示关键字段区块 / 移除 HEIC 提示

### 现状
- 当前环境未安装 rapidocr：`/api/analyze` 返回 `ocr.available=false`，`fields` 全部为空字符串。
- 页面仍渲染「关键字段」卡片（空表格）和「OCR：未启用…」提示，信息噪音大；
  拖拽区下方还有「支持 JPG / PNG / BMP / WebP（HEIC 需安装 pillow-heif）」提示。

### 处理
- `renderAnalyze()` 根据 `result.ocr.available` 控制 `#fieldCard` 显隐：
  - 无 OCR：隐藏整张卡片，不渲染字段，不显示 OCR 状态文案；
  - 有 OCR：恢复显示并渲染字段（安装 rapidocr 后无需改代码）。
- 删除首页拖拽区下方的格式/HEIC 提示行。

### 涉及文件
- `app/web/app.js:205-215`（hasOcr 显隐）。
- `app/web/index.html`（删除 `.dz-sub` 行）。

## 4. 相关发现（本次未修，建议后续 session 处理）

1. **响应 envelope 不统一**：`/api/batch/{id}` 已修；建议全量接口统一 `{code, error, ...}` 并加契约测试，避免再次出现「undefined !== 0」。
2. **批量轮询携带完整 `annotated_b64`**：每 600ms 轮询会传输每张图的 base64（百 KB 级），多图时浪费带宽/内存；建议轮询结果剔除 `annotated_b64`，或按需单独取图。
3. **历史表存储整段结果 JSON（含标注图）**：16 行约 5MB，长期会膨胀；建议 `add_history` 时剔除 `annotated_b64`（详情需要时再按需生成/缓存），或加容量治理。
4. **前端缺少契约测试**：本次 `HTTP 200` 属于前后端契约漂移；建议加轻量 DOM/接口契约测试（或可选 Playwright）。
5. **服务启动环境**：受限 TEMP 会触发本条问题；建议启动脚本/健康检查输出 TEMP 可写性，或在 README 说明「请从普通终端启动」。
6. **OCR 能力**：当前未安装 rapidocr；若需要字段能力，安装 `requirements-ocr.txt`。README 可补充「无 OCR 时仅做翻拍判定，字段区块自动隐藏」。
